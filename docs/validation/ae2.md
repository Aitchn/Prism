# Validation: Applied Energistics 2 on Prism

`validation/ae2` rebuilds the core of Applied Energistics 2 as a plain plugin on `prism-api`. It is a **test of Prism**,
not a product: the goal is to find out which parts of a storage-network mod Prism can already express and which parts
it cannot. Textures are placeholders generated by a script; nothing here is published.

## What is implemented

| AE2 feature | Here | Prism platform used |
|---|---|---|
| Cables, dense cables, controller | Connectivity, shortest-path channel routing (8 per cable, 32 dense), controller conflicts | `BlockPlaceBehavior`, `BlockRemoveBehavior`, `BlockLoadBehavior` (nodes join and leave as chunks load) |
| Power | Idle drain, energy cells that keep their own share in per-block data, creative cell, energy carried across merges and splits | `CustomBlock.data()`, `BlockTickBehavior` on the controller, `BlockCapability` (`ae2:energy_sink`) |
| Drives and storage cells | 1k to 256k cells with AE2's byte model; a cell is an item whose contents are its own data | `ItemService.editData`, `ItemLoreBehavior`, per-block data, `ContainerMenu` |
| Terminal | Real container: stored items, left click a stack, right click one, input row, shift-click from the inventory, live refresh | `ContainerMenu` (`SlotRole`, `refreshTicks`) |
| Patterns | Blank and encoded patterns, encoder GUI and `/ae2 encode`, pattern provider with nine pattern slots | `ContainerMenu`, per-stack and per-block data |
| Autocrafting | Recursive planner, byte cost, jobs on crafting CPU clusters (flood fill) | `MenuSpec` for the request flow |
| Looks | Controller, drive, terminal and provider switch between `offline` and `online`; drive, terminal and provider face the placer | `prism:variants`, `prism:rotation`, `BlockService.setVariant` |
| Survival | 29 crafting recipes make every item (the encoded pattern comes from the encoder) | `prism/recipes/*.yml`, `prism:shaped`, `prism:shapeless` |

Certus quartz has no ore because Prism has no world generation yet: `certus_quartz_crystal` is made from quartz and
lapis. The creative energy cell needs a nether star so that every item can be obtained in survival.

Not attempted: import/export/storage buses, interfaces, P2P tunnels, wireless, spatial storage, facades, cable colours,
security, quartz growth and world generation. The buses and interfaces are blocked by the gap on virtual inventories
below.

The grid, storage and crafting logic (`grid/`, `storage/`, `crafting/`) does not import Bukkit and has unit tests.
`runtime/` and the top-level classes are the Prism adapter. `-Dae2.selftest=true` places real Prism blocks on a live
server (used by the smoke test) and checks the grid, a drive with a cell, the energy capability and per-block data
end to end.

## How the first version differed

The first version of this rebuild (before the block platform, slot menus, item data and recipe registry) had to:
keep its own position index in `DataStore`; write item data with its own persistent data keys; draw the terminal as a
button list that closed and reopened on every click; and offer test items through a command. All of that is gone;
Prism now provides it. The gaps it found then are listed in [platform-triage.md](../platform-triage.md).

## Gaps that remain

1. **Virtual inventories.** `PrismCapabilities.INVENTORY` is a Bukkit `Inventory`. An ME interface, import bus or
   export bus must present the network's storage (millions of items, no slots) to a hopper or another mod's machine.
   Prism needs either a slotless item-handler capability or a documented way to build a virtual `Inventory`.
2. **Connection-dependent shape.** Cables should look different for each combination of connected sides and have a thin
   hitbox. `prism:variants` could list 64 names, but every variant needs a texture or model and the cable would still
   be a full cube to collisions. Needs generated connection variants and non-full hitboxes (triage row 13).
3. **Text input.** The terminal has no search box and the crafting amount is chosen from fixed buttons (triage row 18).
4. **Batch looks.** Switching the look of many blocks at once costs one `runAt` per block. A network of hundreds of
   devices changing state together would benefit from a batched call.
5. **Recipes with data.** A crafting-table recipe that takes an item with per-stack data (a filled cell) does not match,
   because the exact choice compares the whole stack. AE2 avoids it by using data-less components as ingredients.
6. **Lore language.** Lore is a fixed language; there is no per-player translation.
7. **World generation.** No certus ore or meteorites until Prism has a generation hook (triage row 28).

## Not verified

CI proves the content loads, recipes register, the server-side self test passes on Paper, Folia and Purpur, and the
logic is correct. It cannot prove what a player sees or does. See the hand-test list in the pull request.
